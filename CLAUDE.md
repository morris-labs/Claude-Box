# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

This repo defines a sandboxed Docker environment for running Claude Code itself against an arbitrary host project, plus a native desktop GUI (`gui/`, C++/Qt6) for managing those sandboxes: seeing what's running, creating/reopening conversations, and interacting with them in an embedded terminal.

- `Dockerfile` — builds the `claude-code` image (Ubuntu base) with `@anthropic-ai/claude-code` installed globally. The container's built-in uid/gid-1000 user is renamed to match the host username (passed as `--build-arg USER_NAME=$(whoami)`) so file ownership matches the host user, and gets passwordless sudo. The image's `WORKDIR` is `/home/USER_NAME/workspace`, but that's only a fallback: every box the GUI launches overrides it with `-w <target_dir>` (see "How a box is actually launched" below). Otherwise unchanged by the GUI work — it's still just the sandbox image definition.
- `gui/` — the app. See its own section below.

There used to be a set of bash launcher/manager scripts (`claude-box.bash`, `claude-box-manager.bash`, `claude-box-lib.bash`, `claude-box-resume-all.bash`, `claude-box-resume.service`, `docker-compose.yml`) doing all of this from the terminal. They're retired in favor of `gui/`, but intentionally left on disk (untracked — see `.gitignore`) as a working fallback until the GUI has fully replaced them in daily use. Don't extend them further; port improvements to `gui/` instead.

## `gui/` — the C++/Qt6 app

A single-window dashboard: a filterable table of boxes plus a details panel on top (refreshed on a 3s timer), a tab strip of embedded terminals below, and menu-bar/toolbar/context-menu actions (New/Open/Close/Remove/Purge…).

**Keyboard convention — load-bearing.** Every application shortcut is a `Ctrl+Shift` chord (plus `F5` and `Alt+1..9`). This is not stylistic: Qt resolves `QAction` accelerators in `QShortcutMap` *before* the focused widget sees the key, so a plain `Ctrl+N` menu shortcut would be stolen out from under Claude Code running in a terminal pane. `TerminalWidget::event()` handles `QEvent::ShortcutOverride` and accepts every key that isn't a reserved chord, which forces Qt to deliver it as an ordinary key press to the terminal instead. Adding a plain-`Ctrl` shortcut anywhere in the menus will silently break that key inside every terminal — add it to `isApplicationChord()` in `TerminalWidget.cpp` or don't add it.

**Container lifecycle — no tmux.** A box is created with `docker run -d -i -t --rm --name <box> ...` (detached, but with a tty allocated so `claude`'s interactive UI has something to render into, and stdin held open so it can be typed into). Viewing/interacting with it means spawning `docker attach <name>` wired to an app-owned PTY and rendering that in a tab. **`-i` is not optional:** without it the container has no stdin stream, and `docker attach` still renders output but has nowhere to send keystrokes — every terminal tab looks alive and silently swallows typing, so the trust prompt and any message you type go nowhere. The attach side also overrides `--detach-keys` (docker's default Ctrl+P Ctrl+Q would otherwise delay or eat Ctrl+P inside the box). Closing a tab only kills the local `docker attach` client (`docker attach` detaching doesn't stop what it's attached to) — the container keeps running until an explicit `docker stop` (the **Close** action). This is why there's no tmux dependency and no separate crash-signal file: `docker ps` is always the live "is it running" ground truth, so a box that isn't running just shows up as `Known` (reopenable), whether that's because you closed it or the host rebooted.

**Naming.** Containers are always `claude-agent-<base>`, where `<base>` is the issue slug (when the issue workflow fires) or the target directory's basename, run through a sanitizer; collisions get `-2`, `-3`, … appended. Every `docker ps` call filters on `name=^claude-agent-`, so anything outside that prefix is invisible to the app. The two sanitizers in `DockerBackend.cpp` (`sanitizeBoxBase`, `slugifyIssueName`) exist to byte-match the old bash `tr`/`sed` pipelines exactly — keep them ASCII-only rather than "improving" them with Qt's unicode-aware classification, or existing boxes stop resolving.

**Data model.** `~/.claude-box/known/<container-name>` — one `key=value` file per box (`target_dir`, `session_uuid`, `conversation_name`, `yolo`, `model`, `effort`, repeatable `port=`/`dir=`), permanent until an explicit Purge/Remove. `yolo` maps to `claude --dangerously-skip-permissions` — the key kept its old name so existing records still load, but the field and the UI now say what the flag does (`skipPermissions`, "Bypass permission prompts", on by default). `model`/`effort` map to `--model`/`--effort`; both are omitted from the record when left on "default", which means the flag isn't passed and `~/.claude/settings.json` decides. There is no `rc` key any more: `--remote-control` is passed to every box unconditionally, and the old key is ignored where it still appears. `session_uuid` is normally minted host-side with `QUuid::createUuid()` and handed to `claude --session-id` on first creation, so the same conversation can be resumed later via `claude --resume <uuid>` — deliberately not `--continue`, which only grabs "the most recent conversation in this directory" and gets ambiguous once a directory has several tracked boxes. A new box can also *adopt* an existing conversation instead of minting one (see `ConversationCatalog` below), in which case the record simply points at a uuid Claude already had on disk. See `gui/src/BoxRecord.{h,cpp}`.

**Workspace folders.** A box can point its agent at a subfolder of the target directory, named after the conversation ("Emails not sending!" → `Emails_not_sending/`), instead of letting it work in the tree root. **The container still mounts and runs in the base directory either way** — the subfolder is only where the agent is *told* to work, via the opening prompt. That is inherited from the bash launcher and load-bearing: sibling issue folders and the tooling beside them stay visible, and every box for a tree keeps one mount and one `~/.claude/projects` encoding.

In the bash version this was implicit and available to exactly one project — `app.odinhelp.com`, whose `new-issue.sh` the launcher shelled out to. It's now a checkbox in `NewBoxDialog`, available anywhere, and **all it does is create the folder**. Whatever a tree needs *inside* that folder — a repo clone, a copied `.env`, a seeded `CLAUDE.md` — belongs in that directory's own `CLAUDE.md` as instructions to the agent, not in this launcher: per-project provisioning scripted here is knowledge the agent that has to live with it can't read. (`app.odinhelp.com/CLAUDE.md` now spells out the clone and `.env` copy that `new-issue.sh` used to perform; the script still exists and still works by hand, but nothing calls it.)

The slug is used for **everything**: the folder, the container name, the record's `conversation_name`, and `claude --name`. One word identifies a box in a directory listing, in `docker ps` and in the dashboard. The name as it was typed survives in the opening prompt, so the agent still sees the human phrasing. An existing folder is reused untouched — that means you're resuming, not starting fresh — and resuming a box never re-provisions anything. The chosen folder is recorded as `workspace=` for the details panel.

The checkbox's default is remembered per target directory in `QSettings` (both answers, so an explicit "no" sticks). A tree that still carries an executable `new-issue.sh` seeds that as "yes" the first time it's seen: the script isn't run, but its presence is a reliable marker that the tree is organised into per-issue folders.

**How a box is actually launched.** Beyond `-d -i -t --rm --name`, every box gets `--user USER_NAME` (derived from `$USER` at runtime), `-e IS_SANDBOX=1`, `-w <target_dir>`, and three bind mounts: `<target_dir>:<target_dir>` (the host path is reproduced *identically* inside the container — the `~/.claude/projects/<encoded-path>` lookups that Purge and the conversation picker do only work because of this), plus the host's `~/.claude` and `~/.claude.json`. That last mount is why Purge deliberately never touches `~/.claude.json`: it's the live host file, not a per-box copy.

The container doesn't exec `claude` directly. It runs `bash -c '<gitSetup> && shift && exec claude "$@"' _ <target_dir> <claude args...>`, where `<gitSetup>` is `git config --global --add safe.directory "$1"` — collapsing to `true` when the target dir has a `gitconfig` file, since that file already sets `safe.directory = *` and becomes `GIT_CONFIG_GLOBAL`.

**Components (`gui/src/`):**
- `Theme` — the dark palette and stylesheet, applied in `main()` before any widget exists. Hand-built rather than inherited from the desktop theme because the terminal panes are unavoidably dark and a light system theme around them read as two different programs. Widgets that paint themselves (`TerminalWidget`, the table's status dots) read `Theme::` accessors instead of hardcoding colors.
- `Icons` — toolbar/menu icons drawn with `QPainter` at several sizes, not loaded from an icon theme or `.qrc`. Keeps the build free of resource plumbing and guarantees the icons match the fixed dark palette on any desktop.
- `BoxDetailsPanel` — properties view for the selected row: container name, directory, session uuid, flags, ports, mounts. Merges the live `BoxInfo` with the on-disk `BoxRecord`; a box started outside this app has no record and shows dashes rather than another box's settings. Captions stack above values in a plain `QVBoxLayout` — a `QFormLayout` keeps its field column too narrow here and silently clips long values instead of wrapping them.
- `BoxRecord` — the record above: load/save/loadAll (plus a `remove()` that's currently unused; Purge deletes record files by path).
- `DockerApi` — a minimal synchronous client for the **Docker Engine API** over its local socket (`QLocalSocket`, hand-rolled HTTP/1.1 — Qt has no HTTP-over-unix-socket client at all). It exists because `docker stats --no-stream` costs **1–2 seconds per call regardless of container count**, since the CLI waits for a second CPU sample before printing anything; the same data comes back from `GET .../stats?stream=false&one-shot=true` in about a millisecond, once you keep the previous sample yourself and compute the CPU delta across polls (`DockerBackend::statsDetail()` / `m_prevCpu` do that; the formula is docker's own, and was checked against a `--cpus=1` saturated container: 99.79% from this code vs 100.56% from `docker stats`). `QLocalSocket` is a unix socket on Linux and a **named pipe on Windows**, and the Docker Desktop daemon listens on both by the same protocol, so this client is the thing that makes a Windows port not need a second polling implementation — see `socketPath()`'s `Q_OS_WIN` branch, which is the only platform-conditional code in the file. Pinned to API version `v1.44` (`kApiVersion`) so a newer daemon can't change a response shape underneath it.
- `DockerBackend` — every `docker` interaction, now API-first with the CLI as fallback (`DockerApi::isAvailable()` gates every call site): `listBoxes()`/`isRunning()`/`createNew()`/`stop()`/`remove()` all try the socket and only shell out to `docker` when it's unreachable — a `tcp://`/`ssh://` `DOCKER_HOST`, a socket that doesn't exist, anything `DockerApi` deliberately doesn't handle. **This means the polling path is no longer slow at all**: `docker stats`'s 1–2 second cost is gone, so `listBoxes()` no longer needs the 10-second stats cache or a worker thread to stay off the GUI thread on the API path — both stay in place as the CLI fallback's safety net (see the v1.1.0 history in git blame if you need the pre-API numbers: 3 event-loop ticks in 15 seconds, then 1510 ticks after the original fix). `createNew()`'s container-launch parameters are captured once in `DockerBackend::LaunchSpec` and turned into either `docker run` flags (`runContainer()`) or a `containers/create` JSON body (`runContainerViaApi()`) — one description, so the two paths can't drift out of sync with each other. Within that: a `gitconfig` file becomes `GIT_CONFIG_GLOBAL`; an `agent.env` file becomes `--env-file` on the CLI path and is parsed by hand (`KEY=VALUE`, `#` comments, bare `KEY` inheriting from this process) on the API path, since `--env-file` is a CLI convenience with no API equivalent; `--name` is forwarded for any named conversation (it's claude's session display name, and the old launcher always passed it). The per-box `claude` flags common to creating and reopening live in `baseClaudeArgs()` so the two paths can't drift — a box that reopens with different flags than it started with is a miserable bug to chase. `createNew()`'s optional `forkFromUuid` argument is the third mode alongside "mint a uuid" and "adopt an existing one" (see `NewBoxDialog` below): a uuid is still minted for the new box, but the launch args add `--resume <forkFromUuid> --fork-session --session-id <the minted uuid>` instead of a bare `--session-id`, so the new session starts as a copy of `forkFromUuid`'s transcript rather than empty — confirmed against the real `claude` CLI, which writes the fork to its own `<uuid>.jsonl` and leaves the source transcript untouched. Workspace provisioning and the opening prompt run exactly as they would for a brand-new conversation, since forking, unlike adopting, always starts a session that's new as far as claude-box's own bookkeeping is concerned.
- `PtySession` — the one genuinely event-driven piece: allocates a PTY via `forkpty()`, execs a program (`docker attach <name>`) with it, and exposes `dataReady`/`write`/`resize` around a `QSocketNotifier` on the master fd.
- `TerminalWidget` — libvterm-backed rendering (`vterm_input_write` fed from `PtySession::dataReady`, cell grid painted with `QPainter`, keystrokes turned into PTY input via `vterm_keyboard_key`/`vterm_keyboard_unichar`). Leaning on libvterm for VT100/xterm correctness rather than hand-rolling ANSI parsing is the load-bearing decision here — Claude Code's own TUI (color, alternate screen, live-updating status lines) is exactly what a partial terminal emulator renders as garbage. v1 scope note: no scrollback buffer, no text selection. When the attached process exits the widget does **not** close its own tab: it keeps the last screen, dims it, and paints a banner (`isDisconnected()`), because a box can die while you're looking at a different tab and silently removing the terminal loses both the fact and the evidence.
- `BoxTableModel` — `QAbstractTableModel` over `QList<BoxInfo>`, supplying status dots (`DecorationRole`), per-column colors, row tooltips, and a `SortRole` that orders Status by urgency (Running, Stopped, Known) rather than alphabetically. `MainWindow` puts a `QSortFilterProxyModel` in front of it for the filter box, so **every row index arriving from the view must be mapped back through the proxy** before it means anything — and Purge's "is anything running against this directory" check deliberately walks the *source* model, since a filtered-out running box is still a running box.
- `ConversationCatalog` — reads Claude's own transcript store (`~/.claude/projects/<encoded-dir>/<uuid>.jsonl`) so the app can offer conversations it never created: ones started from a bare `claude` in a terminal, or left behind by a purged record. The path encoding is Claude Code's own and replaces **every** non-alphanumeric byte, not just `/` — `…/app.odinhelp.com` becomes `-…-app-odinhelp-com`. (Purge previously hand-rolled a `/`-only version of this and therefore silently missed any directory with a dot in it; it now calls `projectDirFor()`.) Titles come from `custom-title` (what `claude --name` set) first, then `ai-title`, then the opening prompt. Scanning is deliberately byte-level: transcripts run to tens of MB, and JSON-parsing every line to count turns cost ~0.5s per directory versus ~60ms for prefiltered parsing.
- `NewBoxDialog` — the creation form (dir/conversation/name/model/effort/permission-bypass/repeatable port+dir-mount rows). Ports and mounts are entered as separate host and container fields and only joined into docker's `A:B` syntax by the accessors — an empty container field mirrors the host side, which is both the common case and, for mounts, what keeps paths copied out of a box meaningful. Mount rows get their own Browse button, and a host directory that doesn't exist is rejected up front rather than letting docker create it root-owned and unwritable by the container user. The model and effort combos open on the value `claude` itself would use — read from `<target>/.claude/settings.local.json`, `<target>/.claude/settings.json`, then `~/.claude/settings.json`, the same precedence claude applies — rather than on a "leave it to the settings" placeholder, and the flag is then always passed explicitly. A value those files name that isn't in the list (a pinned `claude-opus-5`, say) is inserted and selected rather than dropped. Both re-resolve when the target directory changes, but only until the user picks something by hand; the programmatic selection blocks signals so that resolving doesn't count as picking. The model combo stays editable, since `--model` also takes a full model name; `MainWindow` turns its output into a `BoxRecord` and calls `DockerBackend::createNew`. The conversation combo defaults to "Start a new conversation" and otherwise carries the uuid of an existing transcript to adopt; picking one auto-fills the name field (never overwriting a name typed by hand). `createNew()` switches on `rec.sessionUuid` being pre-set: empty means mint + `--session-id`, set means `--resume` that uuid and skip issue provisioning (which exists to *open* a conversation and is meaningless for one already underway). `MainWindow::confirmConversationAdoption()` refuses outright when a **running** box already holds that uuid — two containers resuming one session would write over each other's transcript — and merely confirms when the owner is only `Known`. `loadForFork()` puts the dialog into a third mode (`MainWindow::onFork`, the **Fork Conversation** action): seeded from an existing box much like edit mode — same target directory, locked, since the fork needs that box's own transcript — but everything else (name, model/effort, permission flag, ports, mounts, remotes) is copied over as an editable starting point rather than locked, because the result is a brand-new box, not a change to the source one. The conversation combo itself stays on "Start a new conversation" and disabled: forking always mints its own session id (`forkSourceUuid()`, kept separate from `sessionUuid()`, which stays empty) rather than adopting the source's, so there's no uuid collision for `confirmConversationAdoption()` to guard against here.
- `MainWindow` — wires all of the above together: the menu bar, toolbar, status-bar counters, filter box, details panel, window/splitter geometry persisted via `QSettings`, the `QTimer`-driven refresh, the tab strip, action enablement by row status (`Open` only for `Known`, `Close` only for `Running`, `Remove` only for `Stopped`-but-not-yet-removed, `Purge` for any row with a directory, `Fork Conversation` for any row with a recorded `sessionUuid`), and `Purge`'s logic (removes `ConversationCatalog::projectDirFor(dir)` plus matching `known/` records for that directory only — never the directory's own contents, never `~/.claude.json`, and refuses while a matching box is running).

**Build (host, not this container — see below):**

```bash
sudo apt install qt6-base-dev cmake build-essential libvterm-dev pkg-config
# qt6-base-dev already pulls in Qt6Network, which DockerApi (see below) needs.
cd gui
cmake -B build
cmake --build build
./build/claude-box-gui
```

If `libvterm-dev` isn't packaged/workable on your host, `QTermWidget` is the documented fallback terminal-widget choice, but would mean reworking `TerminalWidget`.

**Desktop entry.** `gui/packaging/` holds `claude-box-gui.desktop.in` and two icons in `Theme.cpp`'s palette: `claude-box.svg` (a `>_` prompt) and `claude-box-jail.svg` (the Claude mark behind bars, generated by `make-jail-icon.py`). Whichever `CLAUDE_BOX_ICON_SOURCE` points at — the jail one by default — is installed under the single theme name `claude-box`, so swapping artwork never touches the entry's `Icon=` or the `QIcon::fromTheme()` lookup in `main()`. Beware `--` inside an SVG's XML comments: it's forbidden, makes the file non-well-formed, and silently costs you the icon. The `.desktop` is *generated* rather than committed ready-made because `Exec=` needs an absolute path to the built binary, which depends on where the checkout lives: `configure_file` + `file(GENERATE)` produce `build/claude-box-gui.desktop`, and `cmake --build build --target desktop-install` copies it plus the icon into `~/.local/share/{applications,icons/hicolor/scalable/apps}`. Nothing is installed by a plain build. `main()` calls `QGuiApplication::setDesktopFileName("claude-box-gui")` to match; on Wayland there's no WM_CLASS to fall back on, so without that pairing GNOME shows a generic icon in the dash and alt-tab.

`main()` also sets the window icon from the same theme name, with a direct read of the installed file as a fallback, since `QIcon::fromTheme()` resolves nothing until a platform theme is loaded. `desktop-install` runs `gtk-update-icon-cache` too: `~/.local/share/icons/hicolor` already carries an `icon-theme.cache` from other apps, and a stale one hides a newly dropped icon from GTK entirely.

The entry is meant to be launched *by name* (Activities → "Claude Box", or `gtk-launch claude-box-gui`), not by clicking the file. Both copies are nonetheless marked executable and the installed one is flagged `metadata::trusted`, because a `.desktop` without those is a document: clicking it hands it to the default text handler, and a file manager that tries to run it anyway spawns a terminal that flashes and dies. The build-tree copy is easy to click by mistake, which is exactly how that gets discovered.

## Windows port (in progress)

A native Windows build of `gui/` is underway on `main`: commits `ec5a41f`..`4f8e7a7` (phases 1–3 of a larger plan; `git log`/`git show` those for full detail, this section is the durable summary). Phases 1–3 were written on a Linux machine with no Windows toolchain, from documented Win32 APIs and careful manual review, unverified at the time. **That's since changed**: phase 4, done hands-on on the Windows test machine, vendored libvterm, got `claude-box-gui.exe` building clean, and — against a real `claude-agent-*` container on a real Docker Desktop (WSL2 backend) — validated attach, keyboard input, `TerminalWidget` rendering (SGR color, alt-screen via `top`, resize propagating through to the container's `stty size`), and `DockerApi`'s named-pipe branch (`\\.\pipe\docker_engine`, live stats polling). As of this writing that work is uncommitted on the Windows box, not yet folded into `main`. One real bug was found and fixed along the way — see the `PtySession` entry below. Not yet tried: a full end-to-end against the actual `claude-code` image built from this repo's `Dockerfile` (testing so far used a plain `ubuntu:latest` container, sufficient to validate the Windows-specific plumbing itself).

**The core problem this port had to solve.** Several places assumed a box's host directory and its container mount path are the identical string — true only because it happens to hold on Linux, where `rec.targetDir` is already a legal path on both sides of the mount. `ContainerPaths::hostToContainer()` (`gui/src/ContainerPaths.{h,cpp}`) makes that mapping explicit instead: identity on Linux/macOS (zero behavior change, verified against a real box), `C:\Users\name\project` → `/mnt/host/c/Users/name/project` on Windows, where a host path can't be a container path at all and its own drive-letter colon collides with docker's `HOST:CONTAINER` bind syntax. Wired into `DockerBackend`'s two launch paths, `NewBoxDialog`'s mount-default, and — the one that actually matters for correctness, not just mount syntax — `ConversationCatalog::projectDirFor()`, since Claude Code's own `~/.claude/projects/<encoded>` naming is based on whatever `cwd` its process sees *inside* the container, never the host path. `ContainerPaths::splitMountSpec()` exists alongside it because a naive first-colon split of a stored `"HOST:CONTAINER"` mount spec breaks the moment the host half is a Windows path.

**PtySession.** `PtySession.cpp` is renamed `PtySessionUnix.cpp` (forkpty, byte-identical to before); `PtySessionWin.cpp` is a new ConPTY backend, selected by `if(WIN32)` in `gui/CMakeLists.txt`. `PtySession.h`'s public interface (`start`/`isRunning`/`resize`/`write`/`dataReady`/`finished`) is unchanged — confirmed the only thing `TerminalWidget` touches, and every `vterm_*`/`VTerm*` symbol `TerminalWidget` uses is libvterm's own portable C API, so `TerminalWidget.{h,cpp}` needed no changes either. The ConPTY side uses two worker threads, not one: a reader that blocks forever in `ReadFile` (no event loop, so nothing could ever be dispatched to it) and a separate writer with a normal Qt event loop for `write()` calls — sharing one thread doesn't work, since a write queued onto the permanently-blocked reader would sit unserved forever.

**ConPTY gotcha, found by actually running it:** the first live attach opened a tab that immediately reported "Session ended (exit 1)" — `docker attach` itself was printing "cannot attach stdin to a TTY-enabled container because stdin is not a terminal" and exiting. A standalone repro (a probe process spawned the same way) showed the child's std handles were `GetFileType`=DISK/CHAR with `GetConsoleMode` failing, i.e. not console handles at all, despite `PROC_THREAD_ATTRIBUTE_PSEUDOCONSOLE` being set correctly and a valid `GetConsoleWindow()`. Root cause: `CreateProcessW` wasn't given `STARTF_USESTDHANDLES`, so Windows copied *this* (windowless GUI) process's own std-handle values into the child's startup info — and the pseudoconsole attribute does not override std handles that are already populated. `bInheritHandles` and an upfront `FreeConsole()` both made no difference. Fix: before `CreateProcessW`, set `startupInfo.StartupInfo.dwFlags |= STARTF_USESTDHANDLES` and null out `hStdInput`/`hStdOutput`/`hStdError` — with no std handles to inherit, ConPTY wires all three to the pseudoconsole itself. Confirmed against real container output: color (`ls --color`, `grep --color`), alt-screen (`top`, clean restore to the primary buffer on quit), and live resize (window resize → `PtySession::resize` → `ResizePseudoConsole` → the container's own `stty size` changes) all render correctly through `TerminalWidget`.

**libvterm on Windows: resolved.** No vcpkg port exists (`vcpkg search vterm`/`libvterm` both empty against the 2026-08-29 registry) — vendoring is required, as suspected. The Perl code-generation worry (`tbl2inc_c.pl`) turned out to be moot: that concern was checked against the git repo (and Neovim's now-archived fork of it), but the **0.3.3 release tarball is different** — it ships the generated `src/encoding/*.inc` files already, has zero `.tbl` inputs, and doesn't even contain `tbl2inc_c.pl`. Its Makefile's codegen rule is dead code against that tarball (`TBLFILES=$(wildcard src/encoding/*.tbl)` matches nothing). MSVC source compat was also a non-issue in practice — one local patch needed, not the broader porting effort the git-repo/Neovim-fork history implied.

The fix vendors the 0.3.3 tarball's `src/`+`include/` (21 files) into `gui/third_party/libvterm/`, built as a `STATIC` lib (`claude-box::vterm` alias) with `include/` `PUBLIC` and `src/` `PRIVATE` (for the `.inc` fragments and internal headers), `_CRT_SECURE_NO_WARNINGS` plus targeted `/wd4996 /wd4244 /wd4267 /wd4018` for 0.3.3's specific benign MSVC warnings (not a blanket `/w`, to avoid `D9025` fighting the generator's default `/W1`). `gui/CMakeLists.txt`'s `if(WIN32)` branch now does `enable_language(C)` (the project is otherwise C++-only; Linux/macOS never compile a `.c` file, so keeping `C` out of the top-level `project()` call avoids forcing C-compiler detection there too) and `add_subdirectory(third_party/libvterm)`; both platform branches now set a `VTERM_LINK_LIB` variable (`claude-box::vterm` vs. the existing `PkgConfig::VTERM`) that `target_link_libraries` reads, so the non-Windows path is behaviorally unchanged.

The one real source patch, in `gui/third_party/libvterm/include/vterm.h` (marked "claude-box local patch"): `#undef small` after the includes. The Windows SDK's `<rpcndr.h>` (pulled in via `<windows.h>` via Qt) `#define`s `small` to `char`, which corrupts the `unsigned int small : 1;` bitfield in `VTermScreenCellAttrs` into `unsigned int char : 1;` in any translation unit that includes both Qt and `vterm.h` — i.e. `TerminalWidget.h` and its moc output. libvterm's own `.c` files never include Windows headers, so they're unaffected.

**How the Windows side is actually getting tested.** This port is being written jointly by two Claude Code sessions: one in this repo on Linux (which can't compile or run Windows code at all) and a separate Claude Code session running directly on a Windows test machine (launched `claude --rc --dangerously-skip-permissions`), coordinating via the Agent SDK's cross-session messaging (`SendMessage` — the Windows session shows up as a reachable peer, addressed by its `--name`). That mechanism needs a plain top-level terminal `claude` session on the Linux end, not one hosted inside the VSCode extension or the Claude Desktop app — `/status` on a working session shows a `Peer address` line (a unix socket on Linux/macOS, `uds:\\.\pipe\...` on Windows); a session without one can't be reached by `SendMessage`. **The actual failure mode hit and fixed on this machine was a stale CLI version, not the session type**: every locally-installed `claude` binary here had capped out at 2.1.218 (`~/.local/share/claude/versions/`), which never bound a peer socket at all — `/status` showed no `Peer address` line, and `SendMessage` to the Windows box (on 2.1.251) failed with "no agent... reachable" even though the Windows side was correctly bound the whole time. Updating the Linux CLI to 2.1.251 fixed it immediately, no session-type workaround needed. Lesson: if a plain terminal `claude --rc` session shows no `Peer address` in `/status`, check the installed CLI version before assuming the session type is the problem.

**Status as of phase 4: on hold.** Windows build is clean (Debug and Release), and box creation, terminal attach/render/resize, `DockerApi`'s named-pipe path, and Close/Purge have all been validated against real Docker Desktop/WSL2 — see the git log for phase-4 commits. Active work on the Windows clone is paused; picking it back up isn't assumed to need re-verifying everything above, just what changes from here.

**Cross-platform parity is a standing requirement going forward, not a one-time port task.** `gui/` is one codebase with two platform-specific backends (`PtySessionUnix.cpp`/`PtySessionWin.cpp`, the two `ContainerPaths::hostToContainer()` branches, the two `DockerApi::socketPath()` branches, etc.) sharing everything else — `TerminalWidget`, `DockerBackend`'s shared logic, `BoxRecord`, `ConversationCatalog`. A functional change or bug fix made against one platform is not done until it's been checked against the other: either the shared code path means both platforms get it for free (confirm that's actually true, don't assume it), or the platform-specific side needs its own equivalent change. The `GIT_CONFIG_GLOBAL` bug (host path used where Linux always had a container path already, because host and container paths are identical there) is exactly the failure mode this guards against — a Linux-only change silently correct on Linux and silently wrong on Windows. Concretely: a Linux-side change that touches shared code, or either platform's mount/path/env handling, needs the other session (Linux here, Windows via cross-session `SendMessage` per below) to pull and confirm before considering the change finished, not just committed.

## Working in this repo

- `Dockerfile` changes: keep the uid/gid remapping (`USER_NAME` = 1000:1000) in mind — it exists specifically to avoid file-permission mismatches between host and container. Build with `--build-arg USER_NAME=$(whoami)` to match your host username. (The `USER_ID`/`GROUP_ID` build args are currently declared but unused; the remapping is hardcoded to 1000.)
- `gui/` changes: the app now builds clean (no warnings-as-errors configured, no errors) against Qt 6.10.2 and libvterm 0.3.3 on Ubuntu resolute. The libvterm C API surface can shift between versions, so if you're on a different libvterm, `TerminalWidget.cpp` is the first place a build breaks.
- **libvterm gotcha, learned the hard way:** `vterm_screen_set_callbacks()` stores the `VTermScreenCallbacks*` you give it — it does *not* copy the struct. Passing a stack local segfaults on the first byte of container output. `screenCallbacks()` in `TerminalWidget.cpp` exists solely to hand it something with static lifetime; don't "simplify" it back into a local.
- **Also non-obvious:** libvterm only allocates the alternate-screen buffer if you call `vterm_screen_enable_altscreen(screen, 1)`. Without it the altscreen escape is silently ignored and Claude Code's TUI draws over the primary buffer instead of switching — which looks like a rendering bug, not a missing-init bug.
